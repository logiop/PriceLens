1. Panoramica

PriceLens è un’applicazione web di pricing intelligence per l’e-commerce. Monitora i prezzi dei competitor su retailer e marketplace, li confronta con il tuo prezzo, genera alert automatici e — soprattutto — suggerisce il prezzo da applicare con margini protetti.

A differenza di un semplice osservatore di prezzi, PriceLens chiude il ciclo: osserva → analizza → consiglia → applica. Il passaggio finale è un pulsante.

A chi serve

  • Retailer online che vogliono restare competitivi senza erodere il margine.
  • Brand / manufacturer che devono controllare la compliance MAP/MSRP (prezzo minimo pubblicizzato) dei propri rivenditori.
  • Team pricing che hanno bisogno di storico, indicatori e automazioni.

Cosa risolve

Problema Come lo risolve PriceLens
I competitor cambiano prezzo ogni giorno Raccolta automatica periodica (scheduler) + storico
Non sai se sei caro o economico Posizione (1° = più economico) e indice di competitività 0–100
Ribassare il prezzo erode il margine Motore di repricing con floor di margine e ceiling MSRP
Scopri le violazioni MAP troppo tardi Alert critici immediati ad ogni raccolta
I dati restano chiusi in un foglio Excel Export CSV / Excel, API REST, multi-utente

2. Architettura

PriceLens è un monolite modulare a due strati: un backend FastAPI (API REST + serve il frontend compilato) e un frontend React/TypeScript (SPA). Il database è SQLite (zero configurazione, adatto a demo e piccoli deployment).

Flusso di una richiesta

  1. Il browser carica la SPA da http://host:8000/.
  2. La SPA chiama le API con Authorization: Bearer <JWT>.
  3. FastAPI risolve l’utente dal token e filtra tutti i dati per user_id.
  4. Il router calcola statistiche di mercato e restituisce JSON.
  5. Il frontend disegna tabelle, grafici e card.

3. Modello dati

Cinque entità, tutte legate all’utente tramite user_id (multi-tenancy a livello di riga).

User 1───N Product 1───N PricePoint N───1 Competitor
               │
               └──────N Alert

Entità

Entità Campi principali Ruolo
User id, email (unique), password_hash Account proprietario dei dati
Product sku, name, brand, category, cost_price, current_price, msrp, map_price, strategy, min_margin_pct Il prodotto che vendi
Competitor name, domain, type, price_source_type, price_source_config Chi monitori
PricePoint product_id, competitor_id, price, stock_status, captured_at Una rilevazione di prezzo nel tempo
Alert product_id, competitor_id, type, severity, message, read Evento da leggere

Vincoli e indici

  • UniqueConstraint(user_id, sku) — lo SKU è unico per utente.
  • Indice composito (product_id, competitor_id, captured_at) sui PricePoint: rende veloce l’ultimo prezzo per competitor.
  • Indice su captured_at per le query “di oggi” della dashboard.

Perché user_id anche su PricePoint e Alert

Anche se tecnicamente derivabili dal prodotto, tenerli denormalizzati permette di filtrare con una sola condizione (WHERE user_id = ?) le query più frequenti (conteggio alert, punti di oggi) senza join.

4. Autenticazione e multi-utenza

Registrazione e login

POST /api/auth/register   → crea utente, restituisce JWT
POST /api/auth/login      → verifica credenziali, restituisce JWT
GET  /api/auth/me         → profilo corrente

La password non è mai salvata in chiaro:

salt = secrets.token_hex(16)
dk = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt), 600_000)
hash = f"pbkdf2_sha256$600000${salt}${dk.hex()}"

Il confronto usa hmac.compare_digest (tempo costante, niente timing attack).

Token

  • JWT HS256, payload {sub, iat, exp}.
  • Scadenza di default 7 giorni (PRICELENS_TOKEN_EXPIRE_MINUTES).
  • Chiave PRICELENS_SECRET_KEY; se assente ne viene generata una casuale all’avvio (in produzione va impostata fissa).

Isolamento tra utenti

Ogni endpoint applicativo ha la dipendenza CurrentUserDep. Le query includono sempre WHERE user_id = <utente>. Le letture per ID verificano la proprietà:

def _get_owned(session, user_id, product_id) -> Product:
    product = session.get(Product, product_id)
    if product is None or product.user_id != user_id:
        raise HTTPException(404, "Prodotto non trovato")
    return product

Restituire 404 (invece di 403) evita di rivelare l’esistenza di risorse altrui (anti-IDOR).

5. Il ciclo del prezzo: la raccolta

Il collector è il cuore pulsante. Ad ogni “giro” crea un PricePoint per ogni combinazione prodotto attivo × competitor attivo dell’utente.

Fonte simulata (default)

Pensata per demo e test: ogni competitor ha un prezzo “di riferimento” base = current_price × base_ratio e si muove con un random walk mean-reverting:

  • base_ratio — posizione tipica (0.96 = 4% più economico, 1.06 = 6% più caro);
  • volatility — ampiezza del rumore giornaliero;
  • promo_prob — probabilità di una promozione temporanea (−6%…−20%);
  • stockout_prob — probabilità di esaurimento stock.
nuovo_prezzo = ultimo + (base − ultimo) × 0.3 + base × rumore(−vol, +vol)

Il fattore 0.3 è la forza di richiamo: se il prezzo si allontana troppo dalla base, tende a tornare. Ne risultano serie storiche realistiche senza dipendere dalla rete.

Fonte live (URL)

Con price_source_type = "url" il collector scarica la pagina (HTTPX) ed estrae il prezzo con tre strategie configurabili:

selector_type Configurazione Esempio
jsonld (default) — schema.org/Product → offers.price
css selector, attribute meta[itemprop=price] + content
regex pattern (gruppo price) "price"\s*:\s*"?([0-9.]+)

Il parsing degli importi normalizza i formati italiani e internazionali: 1.234,56 → 1234.56, 99.99 → 99.99, € 1 234,56 → 1234.56.

Nota. Lo scraping live va usato solo su siti di cui hai il permesso di leggere i dati, rispettando ToS e robots.txt. In caso di errore il collector incrementa errors e non blocca il giro.

Giro di raccolta

per ogni prodotto attivo:
  per ogni competitor attivo:
     prev = ultimo PricePoint
     prezzo, stock = simula oppure fetch_url
     inserisci nuovo PricePoint
     genera alert confrontando con prev
commit

6. Analisi di mercato

Per ogni prodotto vengono calcolate, al volo, tre grandezze.

Min / max / media

Si considerano solo i competitor in stock con prezzo valorizzato: un prezzo di un prodotto esaurito non è un prezzo realmente acquistabile.

Posizione

Il rango del tuo prezzo tra i prezzi dei competitor:

posizione = (numero di competitor più economici di te) + 1

1 = sei il più economico. N+1 = sei il più caro.

Indice di competitività (0–100)

Un punteggio normalizzato, indipendente dal numero di competitor:

indice = 100 × (N − posizione + 1) / N
  • più economico → 100
  • più caro → 100/N (tende a 0 con molti competitor)

La dashboard media questo indice per dare un colpo d’occhio sulla salute del listino.

7. Motore di repricing

Il repricing trasforma l’analisi in un’azione. Per ogni prodotto calcola:

  1. Floor (pavimento) — sotto cui non si scende mai: max(MAP, costo × (1 + margine_minimo))
  2. Ceiling (tetto) — sopra cui non si sale: MSRP, oppure max competitor × 1.05 se manca l’MSRP.
  3. Target secondo la strategia, poi clamp(floor, target, ceiling).

Le quattro strategie

Strategia Formula (indicativa) Quando usarla
Allinea al minimo (match_min) min − max(0.01, min×1%) Presidio del prezzo più basso
Sottoquotazione (undercut) min × 0.98 Aggressiva, −2% sul minimo
Margine protetto (margin_protected) max(floor, min) Default: competitivi senza perdere margine
Premium (premium) ceiling (MSRP o max×1.03) Posizionamento alto di gamma

Esempio numerico

Prodotto: costo 650 €, margine minimo 15%, MAP 799 €, MSRP 899 €.

  • Floor = max(799, 650 × 1.15) = max(799, 747.5) = 799 €
  • Competitor più economico = 780 €
  • Strategia margin_protected → target = max(799, 780) = 799 €
  • Ceiling = 899 € → il prezzo resta 799 €
  • Margine = (799−650)/799 = 18,6 %

Se invece il competitor scendesse a 760 €, il floor (799) vince ancora: PriceLens ti dice “non scendere sotto 799” — protegge il margine.

Cosa restituisce

Ogni raccomandazione contiene: prezzo suggerito, margine stimato, delta % rispetto a oggi, nuova posizione prevista, floor, ceiling e una spiegazione in chiaro del perché. L’applicazione è un POST /api/repricing/apply che aggiorna current_price.

8. Sistema di alert

Ogni osservazione viene confrontata con la precedente. Se scatta una condizione, viene creato un Alert con severità e messaggio.

Tipo Quando Severità
map_violation prezzo competitor < MAP del prodotto critico
price_drop calo ≥ 3 % avviso
price_rise rialzo ≥ 3 % info
out_of_stock stock passa a esaurito avviso
back_in_stock rientro in stock info

Gli alert sono per-utente, filtrabili per stato (letti/da leggere) e severità, e possono essere esportati. La dashboard mostra gli ultimi e il conteggio degli aperti.

9. Scheduler periodico

Un task asyncio avviato nel lifespan dell’app esegue la raccolta in background:

  • intervallo: PRICELENS_COLLECT_INTERVAL_SECONDS (default 300 s);
  • interruttore: PRICELENS_SCHEDULER_ENABLED=0 per disattivarlo;
  • per ogni utente, esegue collect_round in un thread (asyncio.to_thread), così il calcolo bloccante non ferma il loop degli eventi.

Lo stato è consultabile su GET /api/scheduler/status (enabled, interval_seconds, running, last_run, last_error, last_result).

Con più processi uvicorn ogni processo avrebbe il proprio scheduler: in produzione conviene un solo worker, oppure spostare la raccolta in un job esterno.

10. Export CSV ed Excel

Tre endpoint, tutti filtrati per utente:

GET /api/export/products?format=csv|xlsx
GET /api/export/alerts?format=csv|xlsx
GET /api/export/history/{product_id}?format=csv|xlsx&days=60
  • CSV: generato con la stdlib csv, text/csv; charset=utf-8.
  • Excel: generato con openpyxl, application/vnd.openxmlformats-…sheet.
  • Il file arriva con Content-Disposition: attachment e nome parlante (pricelens-prodotti.csv, pricelens-storico-<SKU>.xlsx).

Nel frontend i pulsanti CSV / Excel scaricano il file via fetch con il token, creano un Blob e avviano il download.

Struttura del codice

├── components/        # Layout, PriceChart, Modal, Badge, StatCard, …
├── lib/
│   ├── api.ts         # client tipizzato + gestione token/401

Pattern di caricamento

useFetch(fn, deps) incapsula caricamento/errore e si ri-esegue quando cambia un “token di refresh” globale. Il pulsante Raccogli prezzi chiama /api/collect e poi refresh(): tutte le viste montate si aggiornano senza ricaricare la pagina.

16. Note operative

iCloud Drive e disco pieno

Se il progetto vive in una cartella sincronizzata con iCloud Drive e il disco è quasi pieno, macOS può rendere i file “dataless” (contenuto evicted). Sintomi: Operation timed out in lettura, venv/node_modules lentissimi.

Soluzioni:

  1. Liberare spazio su disco.
  2. Spostare il progetto fuori da ~/Documents (es. ~/Projects/pricelens).
  3. Tenere il virtualenv fuori da iCloud: python3 -m venv /tmp/pricelens-venv.

Troubleshooting rapido

Sintomo Causa probabile Rimedio
401 su tutte le API token assente/scaduto rifare login
Dashboard vuota su un nuovo utente corretto: i dati sono per-utente creare prodotti/competitor
Attribute "app" not found all’avvio file main.py illeggibile (eviction) riscrivere/ripristinare il file
Porta 8000 occupata vecchio uvicorn pkill -f "uvicorn app.main"
